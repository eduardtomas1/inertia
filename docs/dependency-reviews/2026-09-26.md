## Findings from failed bot CI

### xa11y: exact window geometry

Both [Linux x64](https://github.com/eduardtomas1/inertia/actions/runs/36223619065/job/108353666655)
and [Linux ARM64](https://github.com/eduardtomas1/inertia/actions/runs/36223619065/job/108353666692)
failed the native snapshot scenario. An isolated ARM64 Linux/Xvfb/AT-SPI fixture
reproduced the failure with 0.15.0. On the same Electron 44.4.5 runtime, 0.14.0
passed. The candidate had one accessibility window, but its bounds changed
from the native client `(320,272,640,480)` to the decorated frame
`(319,252,642,505)`. Upstream's
[window geometry implementation](https://github.com/xa11y/xa11y/blob/v0.15.0/xa11y-linux/src/window.rs)
adds `_NET_FRAME_EXTENTS` before converting to logical coordinates.

Inertia now reads those bounded extents from the same authoritative X11 window,
requires an exact client or frame match, and captures only the original client
rectangle. PID, native window ID, title, unique accessibility candidate,
before/after identity checks and protected-field verification still apply.
Unit tests cover scaled geometry, masking, ambiguity and window changes. The
native test independently checks client dimensions using xdotool, masked pixels
and refusal when accessibility is disabled. The fixed 0.15.0 native scenario and
44 Linux snapshot assertions passed in the controlled comparison.

### xa11y: Windows foreground application

The [0.14 Windows provider](https://github.com/xa11y/xa11y/blob/v0.14.0/xa11y-windows/src/uia.rs)
returned the foreground window directly. The
[0.15 provider](https://github.com/xa11y/xa11y/blob/v0.15.0/xa11y-windows/src/uia.rs)
returns a synthetic application root with no bounds and inactive state;
its children are the process-owned top-level windows, whose `active` flag
compares the exact foreground HWND. Inertia removes its old Windows root-as-window
special case and requires one active child on every non-X11 platform.

The regression models an inactive application root containing an inactive main
window and active modal, plus refusal controls for zero or two active windows.
The success control fails against the previous selection code and passes with
the correction. Native Windows capture and mixed-DPI behavior require Windows
CI or a Windows host; these unit controls do not claim native Windows coverage.

### Separate native failures

These original failures are retained as evidence; a passing check on another
architecture does not explain or clear them.

- [Claude PR, Intel macOS gallery](https://github.com/eduardtomas1/inertia/actions/runs/36223665596/job/108353835723):
  the trace spends 24.21 seconds before Electron launch. The shell is online at
  32.29 seconds, the 40 MP image width passes at 41.71 seconds and the preview
  becomes visible at 43.02 seconds. The overall 45-second deadline interrupts
  the next width poll after 1.72 seconds. This does not establish a provider or
  image-decoding regression. The 60-file serial fixture setup needs separate
  measurement on Intel CI; assertions and deadlines are unchanged here.
- [OpenCode PR, macOS ARM64 deny/next-send teardown](https://github.com/eduardtomas1/inertia/actions/runs/36223707220/job/108355927422):
  the runtime stopped and privileged cleanup completed, but Electron 44.4.3
  remained in native window destruction until forced termination 12 seconds
  later. The process sample includes AppKit window-close callbacks. This is
  evidence of a shutdown stall, not proof that the SDK caused it. Focused
  native lifecycle validation accompanies the Electron update.
