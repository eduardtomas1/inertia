# Linux guardian identity contract

Reviewed against PR359 after `b95ae545`. This is a source trace and a documented attestation limitation, not a claim to have patched a privilege-escalation vulnerability. The device/inode fields retain their journal-compatible names and identify the reporting/signalling helper executable. They do not attest the target's `/proc/<pid>/exe`.

## Target authority

| Path | Where the target PID/start comes from | Checks before signalling |
| --- | --- | --- |
| Runtime provider/Git children | `src/node/runtime-owned-processes.ts` `spawnRuntimeOwnedProcess` obtains `child.pid` from the privileged spawn callback and checks `child.spawnfile` against the registry guardian path. Production call sites in the Git runner/worktree code, Codex control/run code, and provider runners wrap the executable through `runtimeOwnedProcessInvocation`. | `admitLinuxGuardian` supplies that PID, `process.pid` and the registry's verified helper identity to readiness. It persists a claim before signalling and rechecks observed claim/owned states. The start time comes from the native `/proc` observation, not provider output. |
| Terminal PTY | `src/server/terminal.ts` creates the platform invocation and wraps the actual `node-pty` process using `spawnRuntimeOwnedPidProcess`. That function receives the returned PTY PID and checks the invocation's guardian command. Its injectable factory is a privileged test/dependency seam. | The same `admitLinuxGuardian` path checks readiness, parent, group/session, start time and helper identity. Renderer terminal requests choose a conversation/session and terminal parameters; they do not supply a guardian PID/start. |
| Runtime claim/stop/release | `RuntimeOwnedProcessJournal.claim` requires a matching pending ownership ID, runtime generation, boot identity and writer capability. Supplied Linux observations are rechecked against the current process identity and expected parent/group. Active stop paths use `claim.linuxIdentity`; failure cleanup retrieves the record by the internally created ownership ID. | `signalLinuxGuardianExact` and its async counterpart use that captured identity and the installed helper. Native `exact_signal_mode` pins a pidfd, checks exact start and allowed state twice, and verifies the helper executable identity. No protocol payload is converted into a target identity. |
| Persisted runtime recovery | `src/main/runtime-owned-process-recovery.ts` reads `journal.records(runtimeGenerationId)`. The journal validates private root/leaf containment and ownership through `direct-runtime-journal.ts`, parses exact record keys, matches the leaf ownership ID and checks record boot identity against its session. | Recovery reads the PID from the validated record, compares the current kernel identity with `RuntimeOwnedProcessJournal.identityMatches`, and requires the hardened stopped, child-free terminal authority before passing the recorded identity to `recoverLinuxGuardianTerminalExact`. Retirement still requires disappearance and process-group cleanup proof. Prior helper fields remain provenance from the claim, not independent target attestation. |
| App-update candidate and its recovery | `src/main/linux-app-update-candidate-process.ts` gets `guardianPid` from its own `spawn` of the verified helper, with the candidate executable held by descriptor. Readiness is read over its inherited pipe, then checked against the same PID/parent/helper. `LinuxAppUpdateCandidateClaimJournal` binds the captured guardian/payload identities to launch, operation, handoff and artifact identities. | Candidate claim/exec signals use the captured guardian. Recovery loads the matching claim, rechecks the observed PID/start and hardened terminal state, records terminal proof and confirms disappearance before releasing ownership. It does not accept a replacement PID from the candidate response. |

The repository architecture keeps these modules in `src/node`, `src/server` and `src/main`. A search of `src/shared` and `src/preload` found no `startTimeTicks`, `guardianExecutable*`, `signalLinuxGuardian*` or `recoverLinuxGuardian*` input surface. Following the production call sites above found no renderer/provider command or output route that substitutes the target PID/start. This is not a claim that same-UID arbitrary native execution or direct modification of private application files is cryptographically excluded.

## Reproduced limitation and disposition

[The non-root Linux ARM64 proof](issue-356-358-linux-helper-identity.json) uses a separate executable that adopts the expected name, group/session and hardening flags. An explicitly invoked low-level helper accepts it and delivers claim/stop signals when given its exact PID/start. Wrong start/helper identities reject and leave it alive. The proposed direct target executable lookup returns `EACCES` with `dumpable=0`.

This agrees with Linux's documented [dumpability restrictions](https://www.man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html) and [proc filesystem access rules](https://www.kernel.org/doc/html/latest/filesystems/proc.html). Changing only the lookup would reject the normally hardened guardian. The reviewed disposition preserves dumpability hardening, helper checks, privileged spawn/record authority, PID/start checks and cleanup requirements, and clarifies the field semantics in source. Process names and helper metadata alone remain insufficient target-executable attestation. A stronger attestation scheme would require a separate design; no such scheme or weakened hardening is introduced here.
